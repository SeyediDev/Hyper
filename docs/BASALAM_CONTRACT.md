## محدودهٔ موجود

Strategy باسلام برای OAuth2 access token و BearerToken فعال است. توکن OAuth از جدول `ExternalOAuthTokens` خوانده و با Data Protection رمزگشایی می‌شود؛ `CredentialsJson` منبع access token نیست. در آستانهٔ انقضا، refresh token روی سرور استفاده و رکورد رمزنگاری‌شده به‌روزرسانی می‌شود.

خواندن توکن به `ConnectionId/ShopId/TenantId/Provider` و فعال‌بودن رکورد محدود است. تمدید زیر تراکنش serializable و قفل `UPDLOCK/HOLDLOCK` انجام می‌شود؛ پس از قفل، نسخهٔ فعلی دیتابیس بدون tracking خوانده می‌شود تا refresh token قدیمیِ context مصرف نشود. فقط ستون‌های همان توکن به‌روز می‌شوند؛ تغییرات ذخیره‌نشدهٔ فراخواننده flush نمی‌شوند. refresh token و scope حذف‌شده از پاسخ حفظ می‌شوند، پاسخ خام قدیمی پاک می‌شود و خطا/لغو پیش از ذخیره، توکن قبلی را حفظ می‌کند. این تضمین تراکنش محلی است: اگر باسلام توکن را بچرخاند ولی پاسخ یا commit از دست برود، بازیابی ممکن است به ورود مجدد نیاز داشته باشد. پس از تمدید، فراخواننده برای کار با entity از قبل trackشده باید آن را دوباره از دیتابیس بخواند.

آدرس ثابت HTTPS: `https://openapi.basalam.com`. redirect HTTP خودکار خاموش است. آدرس دلخواه از credential دریافت نمی‌شود. شناسه‌های غرفه، کالا و تنوع باید عدد صحیح مثبت با نمایش canonical باشند.

دریافت: `GET /v1/vendors/{vendor_id}/products` با page، per_page=100، variants_flatting=false و sort=id:asc. data به همراه total_page/page بررسی می‌شود؛ نبود metadata موجب ادامه تا صفحه خالی می‌شود. شناسه تکراری و پاسخ ناقص موفق تلقی نمی‌شوند. variant[] به اقلام جدا با همان product id و variant id تبدیل می‌شود؛ موجودی variant از stock و موجودی کالای ساده از inventory خوانده می‌شود. Price بدون تبدیل ارز به‌عنوان snapshot خارجی نگهداری می‌شود.

### کنترل کامل‌بودن خواندن کاتالوگ

در مرحلهٔ `ADP-BASALAM` شمارهٔ صفحهٔ پاسخ باید با درخواست یکسان باشد؛ تعدادهای منفی، صفحهٔ خارج از محدوده و تناقض `hasMore` با `total_page` رد می‌شوند. صفحهٔ خالی که ادامه را اعلام می‌کند یا در میانه/انتهای اعلام‌شدهٔ پیمایش قرار دارد، موفقیت نیست. غرفهٔ واقعاً خالی (از جمله `total_page=0`) پذیرفته می‌شود. وقتی تعداد صفحات معلوم نیست، صفحهٔ خالیِ بعدی پایان پیمایش است؛ صرف وجود `total_count` مثبت در این صفحه خطا محسوب نمی‌شود.

آداپتور شناسهٔ کالا را در کل پیمایش و شناسهٔ تنوع را میان همهٔ والدها یکتا بررسی می‌کند؛ مالکیت غرفه و والد تنوع نیز کنترل می‌شود. قبل از اتمام موفق همهٔ صفحات، هیچ کاتالوگی به فراخواننده تحویل نمی‌دهد. خطای قالب/صفحه‌بندی با `CatalogInvalidResponse` و تکرار هویت با `CatalogIdentityConflict` به خطای نهاییِ قابل‌مشاهده در صف تبدیل می‌شود؛ بدنهٔ پاسخ در خطا ذخیره نمی‌شود. پس از رفع علت، بازاجرای کنترل‌شده لازم است. این بررسی‌ها تضمین snapshot تراکنشی از کاتالوگی که هم‌زمان تغییر می‌کند نیستند و تغییر قواعد API رسمی نیز محسوب نمی‌شوند.

تست‌ها: `tools/BasalamTransportChecks` برای parsing و `tools/SynchronizationFlowChecks` برای پیمایش چندصفحه‌ای با توکن اتصال، هویت والد/تنوع، مقادیر صفر/نامعلوم و جلوگیری از فرمان حسابداری هنگام پاسخ نامعتبر. HTTP این آزمون‌ها کنترل‌شده و دیتابیس آزمون دوم موقت است؛ پذیرش زندهٔ باسلام را اثبات نمی‌کنند.

ارسال: `PATCH /v1/products/{product_id}` یا `/variations/{variation_id}`، فقط بدنه `{ "stock": N }`. عدد باید صحیح، غیرمنفی و در محدوده int باشد؛ موجودی کسری بدون قرارداد تبدیل واحد گرد نمی‌شود. موجودی صفر ارسال می‌شود. قبل از PATCH، جزئیات محصول GET شده و vendor.id و عضویت تنوع دوباره بررسی می‌شوند؛ نگاشت اشتباه به غرفهٔ دیگر قابل ارسال نیست.

429، 408 و 5xx در آداپتور قابل بازسعی‌اند. `BasalamAPIError.RetryAfter` زمان اعلام‌شده در پاسخ نهایی را به `IntegrationProviderException.RetryAfter` منتقل می‌کند؛ سپس صف سناریو و Outbox موعد `NextAttemptAtUtc` را در SQL ثبت می‌کنند. زمان بازسعی بزرگ‌ترِ فاصلهٔ سیاست صف و تأخیر provider است؛ سقف فعلی شش تلاش همچنان برقرار است. بدنه خطای provider و credential وارد خطای ذخیره‌شدهٔ صف/داشبورد نمی‌شوند؛ فیلد قدیمی `ResponseBody` در خطای SDK همچنان وجود دارد و نباید لاگ شود.

SDK در پاسخ موقتِ دارای `Retry-After` مثبت، دیگر داخل حلقه منتظر نمی‌ماند یا زمان را به یک دقیقه کوتاه نمی‌کند؛ پاسخ را همان موقع به فراخواننده می‌دهد. بنابراین Worker پیش از timeout، موعد را پایدار ثبت و lease را آزاد می‌کند. این رفتار برای مصرف‌کنندهٔ مستقیم SDK نیز اعمال می‌شود: باید `BasalamAPIError.RetryAfter` را مدیریت کند؛ SDK صف پس‌زمینه نمی‌سازد. بدون هدر معتبر، بازسعی محدود قبلی SDK با `MaxRetries` ادامه دارد. هدر صفر یا تاریخ گذشته به صفر تبدیل می‌شود و بازسعی داخلی محدود را مجاز می‌کند؛ هدر نامعتبر تأخیر ساختگی ایجاد نمی‌کند. هر دو قالب seconds و HTTP-date پشتیبانی می‌شوند.

401 حتی با هدر `Retry-After` فعلاً خطای نهایی است؛ refresh پیشگیرانهٔ توکن نزدیک انقضا مستقل از بازیابی پس از 401 است. تست‌های کنترل‌شدهٔ SDK و SQL شامل 429/503 در خواندن کاتالوگ و ارسال موجودی/مشخصات، عدم ارسال پیش از موعد، بازیابی با context/client جدید، حفظ هویت/نسخه/بدنه و سقف تلاش‌اند. این زمان‌بندی مربوط به همان پیام است، نه محدودکنندهٔ سراسری نرخ غرفه یا provider؛ سایر پیام‌ها و مصرف‌کنندگان مستقل را متوقف نمی‌کند.

## حدود تأیید

آزمون HTTP کنترل‌شده مسیر، paging، variant، صفر، مقدار کسری/منفی، مالکیت غرفه و خطاها را بررسی می‌کند. هیچ PATCH واقعی به غرفه انجام نشده است. برای پذیرش نهایی، حساب تست با توکن مجاز، فروش/خرید واقعی staging، بررسی واحد کالا و رفتار remote لازم است.

ثبت webhook و اعتبارسنجی Bearer اختصاصی اتصال پیاده شده‌اند؛ HMAC داخلی به باسلام نسبت داده نمی‌شود. فهرست رسمی ۹ رخداد و قالب پیام متنی در 2026-09-26 بررسی شد. قرارداد کامل metadata تحویل، payload سفارش/مرسوله/تجربه و پذیرش زنده هنوز کامل نیستند؛ جزئیات و حدود تست در [قرارداد تحویل وب‌هوک](BASALAM_WEBHOOK_DELIVERY.md) ثبت شده است.
