# اجرای پردازش‌گر مستقل هایپریک

پروژه‌های `src/IntegrationWorker/Hyper.IntegrationWorker.Application` و `Hyper.IntegrationWorker.Host` به solution اضافه شده‌اند. Application از قرارداد Domain استفاده می‌کند؛ SQL و HTTP در Infrastructure هستند. الگوی Neo Outbox/ProcessOutboxRecurringJob و OutboxMessageProcessor مرور شد، ولی جدول‌های پایه Neo و repository قدیمی Club در این میزبان ثبت نمی‌شوند.

## تنظیمات

ConnectionStrings__Domain را در محیط اجرای سرویس تنظیم کنید، یا HYPER_SETTINGS_FILE را به فایل تنظیمات امنِ موجود دارای ConnectionStrings.Domain اشاره دهید. رمز در مستندات یا appsettings جدید Worker تکثیر نشده است. برای معماری جدا، `ConnectionStrings__IntegrationConnection` باید دیتابیس مستقل Integration را انتخاب کند. دادهٔ حسابداری از HTTP API خوانده می‌شود؛ Worker نباید برای خواندن `TBL_*` مستقیماً به دیتابیس حسابداری متصل شود. نبود IntegrationConnection هنوز fallback قدیمی Domain را فعال می‌کند؛ در استقرار جدید آن را صریح تنظیم کنید.

```powershell
$env:HYPER_SETTINGS_FILE = 'E:\SJVS\Projects\Hyper\Backend\src\CustomerPortal\Hyper.CustomerPortal.Api\appsettings.json'
dotnet run --project src/IntegrationWorker/Hyper.IntegrationWorker.Host
```

این فرمان سرویس را واقعاً اجرا می‌کند و پیام آماده را به provider ارسال می‌کند. اجرای تست‌های SQL از آداپتر کنترل‌شده استفاده می‌کند و فرمان بالا را اجرا نمی‌کند.

## ورودی و وضعیت

`POST connections/{id}/inventory` زیر مسیر integration موجود، MappingId، SourceVersion و Quantity مطلق دریافت می‌کند. هویت و tenant/shop اتصال از مجوز سمت سرور محدود می‌شود. SourceVersion باید برای همان mapping افزایشی و پایدار باشد. تکرار همان نسخه/بدنه همان MessageId را برمی‌گرداند؛ نسخه قدیمی یا بدنه متفاوت رد می‌شود. این API باید از مقدار قطعی هایپریک تغذیه شود.

`GET connections/{id}/outbox` وضعیت را بدون payload یا credential می‌دهد. `POST connections/{id}/outbox/{messageId}/retry` تنها خطای نهاییِ آخرین نسخه را دوباره صف می‌کند؛ پیام قدیمی پس از نسخه جدید قابل replay نیست.

وضعیت‌ها: ۰ انتظار/بازسعی، ۱ lease ارسال، ۲ ارسال‌شده، ۳ خطای نهایی. داشبورد ادمین آمار و ۳۰ پیام آخر را در زمینه مغازهٔ انتخابی نمایش می‌دهد. شمارش روابط مستقل است.

claim با lease، قفل session در SQL به تفکیک اتصال و ترتیب پیام‌ها انجام می‌شود. قفل در طول HTTP نگه داشته می‌شود تا lease منقضی‌شده باعث سبقت پردازش‌گر زنده نشود. lease دو دقیقه و مهلت ارسال یک دقیقه است. پس از قطع پردازش، lease قابل بازیابی است. تأیید پایان به LeaseId محدود است. تضمین تحویل حداقل یک‌بار است؛ قطع SQL/شبکه ممکن است ارسال مطلق را تکرار کند. موفقیت ارسال، اتمام تراکنش حسابداری یا جلوگیری کامل از overselling را ثابت نمی‌کند.

## خواندن خودکار موجودی از API حسابداری

طبق DEC-005 مرجع، کل موجودی مغازه پس از کسر رزروهاست. capture مقدار Stock و CanSell را از API مستقل حسابداری می‌خواند و فقط رزروهای Integration با Status=0 و ReleasedAtUtc=NULL را از دیتابیس خودش جمع می‌کند. مالک خواندن `TBL_Product.ACCOUNTINGSTOCK_` لایهٔ حسابداری است. کالای غیرقابل‌فروش موجودی قابل ارسال صفر دارد. فیلتر مغازه و tenant الزامی است. مقایسهٔ snapshot و ثبت outbox با transaction واحد Integration انجام می‌شوند؛ آخرین payload موجودی checkpoint مقایسه است و SourceVersion میان تمام عملیات همان mapping مشترک است. تغییر کاهش و بازگشت به مقدار قبلی، اگر هر دو توسط polling دیده شوند، نسخهٔ جدید ایجاد می‌کند.

فرض ASM-001 هنوز نیازمند تأیید است: عملیات واقعی خرید/فروش باید ACCOUNTINGSTOCK_ را به‌روز کند و رزروها قبلاً از آن کم نشده باشند. ازاین‌رو `IntegrationInventoryCapture:AccountingStockSourceVerified` پیش‌فرض false است. فعال‌سازی پس از تأیید این فرض، capture را با فاصلهٔ پیش‌فرض ۳۰ ثانیه پس از پایان هر نوبت اجرا می‌کند؛ trigger/CDC یا تغییر ساختار جدول قدیمی ایجاد نمی‌شود. اکنون مالک نسخه‌گذاری هر نگاشت در دیتابیس Integration نگهداری می‌شود: رویداد حسابداری و capture برای همان نگاشت هم‌زمان مجاز نیستند، حتی با تنظیمات متفاوت دو میزبان. مهاجرت، انتخاب و تعویض مالک در [قرارداد مالک نسخه‌گذاری](INTEGRATION_VERSION_SOURCE.md) آمده است.

این polling مقدار نهایی را همگام می‌کند و event log همهٔ تغییرات میانی نیست. تا تأیید منبع، producer خرید/فروش به‌عنوان تکمیل‌شده گزارش نمی‌شود. رزرو/صدور فاکتور و همگام‌سازی مشتریان همچنان کار جدا هستند.

در اسکن خودکار، خطای شناخته‌شدهٔ سرویس (`IntegrationProviderException`)، خطای
HTTP یا timeout یک نگاشت، پس از خروج از تراکنش همان تلاش، مانع بررسی نگاشت‌های
بعدی نمی‌شود. آن تلاش در شمارش پیام‌های تولیدشده نیست و هیچ مقدار جایگزین یا
موجودی صفرِ فرضی ثبت نمی‌شود؛ نوبت بعدی دوباره منبع حسابداری را می‌خواند. فقط
شناسهٔ اتصال/نگاشت و نوع خطا لاگ می‌شود، نه متن exception یا پاسخ سرویس.
لغو میزبان و خطای SQL/ناشناخته همچنان کل نوبت را متوقف می‌کنند تا scope معیوب
دوباره استفاده نشود. تعارض مالک نسخه همان رفتار skip قبلی را دارد.
این تغییر retry فوری یا cooldown پایدار `Retry-After` برای capture اضافه نمی‌کند؛
محدودیت قبلی فاصلهٔ اسکن برقرار است. فراخوانی مستقیم `ReconcileOneAsync` نیز
خطا را به صف سناریو برمی‌گرداند و از سیاست retry همان صف استفاده می‌کند.

آزمون `dotnet run --project tools/InventoryCaptureChecks` سیاست تولیدیِ هر تلاش
را با عملیات کنترل‌شده بررسی می‌کند؛ اجرای واقعی SQL، تراکنش، HTTP، انتشار
موجودی یا producer حسابداری را اثبات نمی‌کند و capture را فعال نمی‌کند.

- [x] **WRK-STARTUP-201**: خود میزبان ساخته‌شده Worker با SQL محلی و صف خالی اجرا شد؛ startup و polling بدون خطا تأیید شد. capture صریحاً غیرفعال بود و فقط همان پردازش آزمایشی پایان داده شد. تنظیمات اصلی اتصال و TLS تغییر نکردند؛ shared-memory بدون encryption صرفاً override محلی آزمون بود.

## راه‌اندازی صف سناریو و تست رویداد

صف سناریو اکنون به تفکیک **فروشگاه** قفل و مرتب می‌شود؛ اتصال‌های یک فروشگاه
نمی‌توانند از قدیمی‌ترین پیام فعال آن سبقت بگیرند، حتی اگر آن پیام در انتظار
retry باشد. این قاعده با Outbox متفاوت است که همچنان قفل به تفکیک اتصال دارد.
پیش از استقرار، همهٔ پردازش‌گرهای سناریوی نسخهٔ قدیمی (از جمله میزبان پنل در
صورت پردازش صف) باید متوقف و پردازش جاری آن‌ها تمام شود؛ قفل قدیمی به تفکیک
اتصال با قفل جدید فروشگاه هماهنگ نیست و اجرای هم‌زمان دو نسخه مجاز نیست.
ادغام کد هیچ سرویس زنده‌ای را متوقف یا مستقر نمی‌کند.
آزمون `tools/QueueSchedulingChecks` انتخاب صف و ترجمهٔ SQL را بدون اتصال به
دیتابیس بررسی می‌کند؛ پذیرش قفل و بازیابی واقعی SQL همچنان جداست.

1. اسکریپت محدود `docs/schema/ensure-integration-scenario-jobs.sql` را روی دیتابیس اتصال پروژه اجرا کنید. این جدول جدید است و جدول legacy را تغییر نمی‌دهد. در محیط محلی Hyperyek اجرا شده است.
2. Worker.Host باید با همان دیتابیس پنل اجرا شود (`ConnectionStrings__Domain`). پنل همچنان از تنظیمات اتصال خودش استفاده می‌کند. رمز در مستندات یا command ثبت نشود.
3. وارد `/merchantsimulation` شوید، مغازه را انتخاب کنید و در بخش «دریافت رویداد آزمایشی» اتصال، آیتم و محرک را انتخاب کنید. فقط اتصال‌های همین مغازه نمایش داده می‌شوند؛ بدون اتصال، فرم ارسال فعال نیست.
4. POST `/MerchantSimulation/ReceiveScenario` درخواست را در صف ثبت می‌کند؛ refresh صفحه، وضعیت/خطا/خلاصه مغایرت‌ها را نشان می‌دهد. Worker مسیرهای مستقل capture، Outbox و صف سناریو دارد؛ جزئیات اجرای آن‌ها در بخش زیر است.
5. دریافت و ثبت رویداد موفقیت همگام‌سازی نیست. شاخهٔ webhook کالا با نگاشت معتبر، اطلاعات provider را دوباره می‌خواند و از HTTP API حسابداری استفاده می‌کند. تغییر موجودی با منبع تأییدشده به Outbox می‌رود. مرز وضعیت پیاده‌سازی و پذیرش واقعی در [سناریوی دوطرفه](BIDIRECTIONAL_SYNC_ACCEPTANCE.md) ثبت شده است؛ وجود handler را به معنی تکمیل همهٔ سناریوهای مالی تلقی نکنید.

آزمون: `dotnet run --project tools/ScenarioChecks/ScenarioChecks.csproj -- src/AdminPanel/Hyper.AdminPanel.Web/appsettings.json` شامل SQL واقعی با rollback است. در این آزمون آداپتر fake استفاده می‌شود و هیچ تماس HTTP خارجی انجام نمی‌شود. ۲۳ بررسی در 2026-09-15 موفق بود.

## اجرای مستقل سه مسیر (WRK-001)

Worker سه حلقهٔ مستقل را اجرا و هنگام shutdown منتظر پایان هر سه می‌ماند:

- Capture: خواندن وضعیت حسابداری و تولید پیام موجودی، فقط با مجوز تنظیم موجودی قبلی.
- Outbox: ارسال پیام‌های موجود به provider.
- Scenario: پردازش Inbox/وب‌هوک و سایر سناریوهای صف‌شده.

هر نوبت scope و DbContext مستقل دارد. خطای اتصال، DI، پردازش یا dispose یک مسیر
باعث توقف دو مسیر دیگر نمی‌شود؛ همان مسیر پس از فاصلهٔ تنظیم‌شده دوباره تلاش
می‌کند. هر مسیر حداکثر یک عملیات جاری دارد. صف پر پس از هر پیام فرصت اجرا را
به سایر کارها می‌دهد؛ صف خالی یا خطادار منتظر می‌ماند. لغو میزبان به عملیات
جاری و انتظارها منتقل می‌شود. فقط نام مسیر و نوع exception لاگ می‌شود، نه
متن خطا، credential یا payload. قفل‌ها، ترتیب پیام و سیاست retry پایدار همچنان
مسئولیت پیاده‌سازی صف‌اند و با این تغییر جایگزین نمی‌شوند.

تنظیمات اختیاری `IntegrationWorker` (هیچ‌کدام capture یا ارسال واقعی را فعال نمی‌کنند):

```json
{
  "IntegrationWorker": {
    "CaptureInterval": "00:00:30",
    "IdleDelay": "00:00:05"
  }
}
```

مقدار هر فاصله باید بین یک میلی‌ثانیه و یک ساعت باشد؛ مقدار نامعتبر در startup
رد می‌شود. CaptureInterval از پایان هر نوبت محاسبه می‌شود تا captureها هم‌پوشانی
نداشته باشند. تولید رویداد تراکنشی حسابداری و سیاست قیمت/عنوان جزو تکمیل این میزبان
نیستند. جلوگیری از تداخل دو منبع نسخه‌گذاری در لایهٔ Outbox و قرارداد بالا اعمال می‌شود.

آزمون جدید `dotnet run --project tools/WorkerExecutionChecks` خود کلاس تولیدی
Worker.Application را با سرویس‌های scoped کنترل‌شده اجرا می‌کند؛ شامل کندی هر
مسیر، خطا و retry، لغو واقعی، scope مستقل، خطای DI/dispose و عدم افشای خطاست.
این آزمون SQL یا HTTP خارجی ندارد و میزبان production را اجرا نمی‌کند. آزمون
SQL مسیرهای دامنه همچنان `tools/SynchronizationFlowChecks` است؛ این دو شاهد
جای اجرای زندهٔ باسلام یا بیلد کل solution را نمی‌گیرند.

## خطاهای ارتباط با API حسابداری

پاسخ‌های موقت 408، 429، 500، 502، 503 و 504 در مسیر حسابداری به retry پایدار
تبدیل می‌شوند؛ `Retry-After` در کنار backoff صف رعایت می‌شود. کلاینت HTTP خودش
دوباره فرمان را ارسال نمی‌کند. پاسخ موفق نامعتبر یا ناسازگار با قرارداد نیز
به‌عنوان ACK پذیرفته نمی‌شود. جزئیات و محدودیت‌های این مرحله در
[قرارداد HTTP حسابداری](INTEGRATION_ACCOUNTING_HTTP.md) آمده است.
